> 対象: Minecraft Java Edition のワールド（Anvil 形式）

## 1. 目的と範囲

公式の「ワールドの最適化」（`--forceUpgrade`）が扱わない部分を、安全かつ設定なしで整理する CLI。

| 担当する | 担当しない |
|---|---|
| 不要チャンクの削除（GC） | チャンクの中身の形式変換（DataFixerUpper の役割） |
| GC したリージョンファイルの詰め直し | 地形の再生成 |
| 確実に不要なファイルの削除（clean） | プレイヤーの痕跡による推測的な判定 |
| ワールド全体の診断（scan） | 元のワールドの直接の書き換え |

## 2. 基本方針

| ID | 方針 |
|---|---|
| P-1 | **元のワールドには決して書き込まない。** 結果は新しいフォルダに書き出す（[spec/output.md](spec/output.md)） |
| P-2 | 元のワールドとの入れ替え（書き戻し）は、ユーザーが手動で行う。ツールは手順を表示し、`wgc verify` で入れ替えてよいかを確かめられるようにする |
| P-3 | ゴミ箱は持たない。元のワールドを残しておくことが、復元の手段になる |
| P-4 | 自動で削除するのは、確実に安全と言えるものだけ。判断できないものは残す |
| P-5 | チャンクの中身は再エンコードしない。必要なフィールドだけを読み、残すチャンクは元のバイト列のまま書く |
| P-6 | 判定の結果は1つの「計画」（Plan）にまとめ、scan、見積もり、実行のすべてが同じ計画を使う |
| P-7 | 出力は、書き終えた後に元のワールドと突き合わせて自動で検証し、通った場合だけ完了とする |

## 3. コマンドの概要

```
wgc scan   <path> [--json <file>]          # 診断（読み取りのみ）
wgc gc     <path> [--out <dir>] [...]      # --out がなければ見積もりのみ
wgc clean  <path> [--out <dir>]            # --out がなければ見積もりのみ
wgc verify <path> <out>                    # 書き戻してよいかの確認
```

`<path>` は、バニラではワールドフォルダ、Bukkit 系（Paper など）ではサーバーのルートフォルダ。詳細は [spec/cli.md](spec/cli.md)。

## 4. 用語

| 用語 | 意味 |
|---|---|
| ワールドフォルダ | `level.dat` があるフォルダ。Bukkit 系の旧レイアウトでは、ディメンションごとに別のワールドフォルダがある |
| ディメンションフォルダ | `region/`、`entities/`、`poi/` を直接持つフォルダ |
| 種別（kind） | `region`、`entities`、`poi` のどれか |
| リージョン三つ組 | 同じディメンション、同じリージョン座標の `region`、`entities`、`poi` の3ファイル。処理の単位 |
| チャンクの位置 | リージョン座標とファイル内のインデックスから求めた絶対チャンク座標。NBT の `xPos`／`zPos` ではない |
| 削除候補 | InhabitedTime が 0 のチャンク |
| 保護 | 削除候補だが、規則によって残すこと |
| そのままコピー | 内容を一切変えずにファイルを出力にコピーすること |

## 5. 技術構成（P0）

| 項目 | 方針 |
|---|---|
| 言語 | Rust（edition 2024） |
| 構成 | Cargo ワークスペース。`crates/core`（クレート名 `wgc-core`、解析と処理）と `crates/cli`（クレート名 `wgc`、バイナリ） |
| core のモジュール | `region`（P1）、`nbt`（P2）、`layout`（P3）、`plan`（P4）、`trust`（P5）、`report`（P6）、`output`（P7） |
| 依存の向き | `cli` → `core`。`core` は CLI の依存（clap など）を持たない。`core` は端末に出力しない |
| NBT | nanonbt。`core::nbt` の中だけで使う（[spec/chunk-nbt.md](spec/chunk-nbt.md)） |
| 並列化 | リージョン三つ組の単位で並列に処理する |
| エラー | `core` は型つきのエラーを返す。メッセージの整形は `cli` が行う |

P0 の完了条件: ワークスペースに変換し、`cargo build` と `cargo test` が通り、`wgc --help` が動く。

## 6. テストの方針（全フェーズ共通）

- 各フェーズの文書の「受け入れ条件」を、自動テストで満たす。
- テスト用のワールドは、小さな合成データ（テスト内で生成するリージョンファイル）を基本にする。実際のワールドから切り出したファイルを使う場合は `tests/fixtures/` に置き、作成したバージョンを README に書く。
- バージョンをまたぐテストでは、少なくとも 1.12 以前（`Level` あり）、1.18 以降、最新の3種類の形式を用意する。

## 9. 対象外と、MVP 以降の候補

### 対象外

| 対象外 | 理由 |
|---|---|
| DataFixerUpper の再実装 | 保守コストが大きく、ワールドを壊す危険がある |
| プレイヤーの痕跡による削除の判定 | 構造物のブロックによる誤検知が多い |
| `.dat_old` の削除 | ゲーム自身の復旧手段で、消しても効果がない |
| ゴミ箱、チャンク単位の復元 | 元のワールドを残すことで代える |
| ユーザーが指定する保護範囲 | MVP では入れない |
| サーバーの種類の履歴（`ServerBrands`）による判定 | 現在の構成だけを見る。過去の時期の危険は、プレイヤーの位置の確認で部分的に拾い、残りは README に書く |

### MVP 以降の候補

| 機能 | 概要 |
|---|---|
| 自動の入れ替え（`wgc swap`） | ロックの再取得、`verify` 相当の確認、ディレクトリの rename による入れ替え |
| 元のワールドを直接書き換えるモード | 空き容量が足りない巨大なワールド向け |
| 旧形式の掃除 | `.mcr`、`level.dat_mcr`、`villages*.dat` を中身で判定して削除する |
| HTML レポート | `scan` の結果を地図やグラフで表示する |
| 単体のデフラグ・再圧縮 | GC をしない人向け |
| しきい値による削除 | 上級者向けのオプション |
| 公式の最適化の自動実行 | サーバーの jar で `--forceUpgrade` を実行し、前後の差分を出す |

## 10. 設計判断の要約

| 判断 | 理由 |
|---|---|
| 新しいフォルダに書き出す | 途中で止まったときの順序制御、ジャーナル、ゴミ箱が不要になる。元のワールドとの突き合わせで強い検証ができる。増える容量は GC 後のサイズだけ |
| 書き戻しは手動 | 元のワールドを手放す最後の判断を、人間に残す |
| 判定は InhabitedTime だけ（`Status` は使わない） | `Status` はバージョンの変換で書き換わる。InhabitedTime はどの変換でも引き継がれる |
| 保護の規則（強制読み込み、スポーン、構造物の参照） | InhabitedTime が 0 でも、プレイヤーがいないまま中身が動きうる場所を守る |
| ワールドの構成は sekai（TMCJapan/sekai）と同じ方式で認識する | 4種類のレイアウトを、決定的に判定できる |
| 計画と実行を分ける | 見積もりと実際の結果がずれる不具合を、構造的に防ぐ |
