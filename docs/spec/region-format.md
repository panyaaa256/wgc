# リージョンファイル（P1）

実装先: `core::region`。NBT は扱わない。

## ファイル名

- `r.<rx>.<rz>.mca`。座標は符号つき10進整数として解釈する（ゲームと同じく `r.00.00.mca` も受け入れる）。
- 形式に合わないファイルは、リージョンファイルとして扱わない。
- 外部ファイル: 同じフォルダの `c.<cx>.<cz>.mcc`（絶対チャンク座標）。

## 構造

### ヘッダー（8192 バイト）

| 範囲 | 内容 |
|---|---|
| 0〜4095 | 位置テーブル。1024 × 4 バイト。上位 3 バイト（BE）が開始セクタ、下位 1 バイトがセクタ数。1 セクタ = 4096 バイト |
| 4096〜8191 | タイムスタンプ。1024 × u32（BE） |

- 4 バイトとも 0 ならチャンクなし。
- `cx = rx * 32 + (i & 31)`、`cz = rz * 32 + (i >> 5)`。

### ペイロード

開始セクタ × 4096 の位置に、`u32 長さ L（BE、圧縮方式の1バイトを含む）` + `u8 圧縮方式` + `L - 1` バイトのデータ。この `4 + L` バイトをペイロードと呼ぶ。

## 圧縮方式

| 値 | 意味 |
|---|---|
| 1 | gzip |
| 2 | zlib |
| 3 | 非圧縮 |
| 4 | LZ4（下記） |
| 127 | カスタム。展開しない（内容エラー C-1） |
| 上記 + 128 | データは外部ファイルにある。外部ファイルの中身は、下位 7 ビットの方式で圧縮されたデータそのもの。リージョン側のペイロードは通常 `L = 1` |
| その他 | 内容エラー C-1 |

### LZ4

標準の LZ4 フレームではなく、lz4-java の `LZ4BlockOutputStream` の形式。

- 各ブロックのヘッダー（21 バイト）: マジック `LZ4Block`（8）、トークン（1。上位 4 ビットが方式 `0x10` 非圧縮 / `0x20` LZ4、下位 4 ビットが圧縮レベル）、圧縮後の長さ（i32 LE）、元の長さ（i32 LE）、チェックサム（i32 LE）。
- ヘッダーの後に、圧縮後の長さの分のデータ。方式が LZ4 なら LZ4 のブロック形式で展開する。
- チェックサムは、展開後のデータの XXHash32（シード `0x9747b28c`）の値を `& 0x0FFFFFFF` したもの。不一致は内容エラー C-1。
- 元の長さが 0 のブロックで終わる。

## エラーの区分

### 構造エラー（ファイル単位）

P4 は、構造エラーのあるファイルを含むリージョン三つ組全体を、そのままコピーにする。見つかったものはすべて集める。

| ID | 条件 |
|---|---|
| S-1 | ファイルサイズが 1 以上 8192 未満 |
| S-2 | 開始セクタとセクタ数の片方だけが 0 |
| S-3 | 開始セクタが 2 未満 |
| S-4 | `開始セクタ × 4096 + 4 + L` がファイルサイズを超える（長さフィールドを読めない場合を含む） |
| S-5 | `L` が 0 |
| S-6 | `4 + L` が `セクタ数 × 4096` を超える |
| S-7 | 2つのチャンクのセクタの範囲が重なる |
| S-8 | 圧縮方式が 128 以上なのに `.mcc` がない |

- 末尾のセクタは 4096 バイトに満たないことがあるので、範囲は実際の長さ（S-4）で判定する。
- サイズ 0 のファイルは構造エラーではなく、チャンクのないファイルとして扱う。
- Paper の 1.16 以前の「Allow Saving of Oversized Chunks」は、リージョンファイルの形式を変えず、余ったデータを同じフォルダの別ファイル（`*.oversized.nbt` など）に書いていた。これらは他のファイルと同じくそのままコピーし、特別には扱わない。

```rust
pub enum StructuralId { S1, S2, S3, S4, S5, S6, S7, S8 }   // 表示と JSON は "S-1" など

pub struct StructuralIssue {
    pub kind: FileKind,
    pub id: StructuralId,
    pub index: Option<ChunkIndex>,   // ファイル全体の問題（S-1）なら None
}
```

### 内容エラー（チャンク単位）

そのチャンクは残し、ペイロードはそのままコピーする。

| ID | 条件 |
|---|---|
| C-1 | 展開できない |
| C-2 | NBT として読めない（P2 で検出） |

```rust
pub enum ContentError {
    Decompress(DecompressError),     // C-1
    Nbt(NbtError),                   // C-2（chunk-nbt.md）
}

pub enum DecompressError {
    UnsupportedCompression(u8),      // 127 と不明な方式
    MissingExternal,                 // 外部ファイルの方式なのに、中身を渡されなかった
    Truncated,                       // ペイロードが 5 バイト未満
    Corrupt,                         // データの破損
    Lz4Checksum,
}
```

## 読み取りの API（例）

- `RegionFile::parse(kind: FileKind, pos: RegionPos, bytes: Vec<u8>, external: &BTreeSet<ChunkPos>) -> RegionFile`（バイト列を所有し、構造エラーの一覧を持つ）
- `issues() -> &[StructuralIssue]`
- `entries()`: 各チャンクの `ChunkIndex`、`ChunkPos`、開始セクタ、セクタ数、タイムスタンプ、`L`、圧縮方式
- `payload(index: ChunkIndex) -> Option<&[u8]>`
- `decompress(payload: &[u8], external: Option<&[u8]>) -> Result<Vec<u8>, DecompressError>`
- `write_region(source: &RegionFile, keep: &[ChunkIndex]) -> Vec<u8>`（下の「書き込み」）

ファイル全体をメモリに読み込んでよい。

## 書き込み

残すインデックスの集合から、新しいファイルのバイト列を作る。

1. 残すチャンクをインデックスの昇順に、セクタ 2 から詰めて置く。
2. ペイロードを元のバイト列のまま書き、4096 バイトの境界まで 0 で埋める。
3. 位置テーブルに新しい開始セクタと `ceil((4 + L) / 4096)` を書く。
4. タイムスタンプは、残すチャンクは元の値、それ以外は 0。

`.mcc` のコピーは P7 が行う。

## 受け入れ条件

- S-1〜S-8 がそれぞれ検出され、正常なファイルでは何も検出されない。末尾のセクタが短いファイルをエラーにしない。
- gzip、zlib、非圧縮、LZ4（実際のワールドのデータ）、外部ファイルのチャンクを展開できる。127 と不明な方式は C-1 になる。
- 書き込んだファイルを解析し直すと、構造エラーがなく、残したチャンクのペイロードとタイムスタンプが元と一致し、サイズが `8192 + Σ ceil((4 + L) / 4096) × 4096` になる。
