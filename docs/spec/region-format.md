# リージョンファイル（P1）

> 前提: [../spec.md](../spec.md) の「用語」。
> 実装先: `wgc-core` の `region` モジュール。
> このフェーズは NBT を扱わない。チャンクのデータは「圧縮方式と、圧縮されたバイト列」として扱う。展開は「圧縮方式」の節の範囲だけ実装する。

## ファイル名

- `r.<rx>.<rz>.mca`。`<rx>`、`<rz>` は符号つきの10進整数。
- ゲームは `r.00.00.mca` のような表記も読む。ファイル名から座標を得る関数は、ゲームと同じく整数として解釈できる表記を受け入れる。
- 同じ座標を指す2つの名前が同じフォルダにある場合は、エラー（どちらをゲームが読むか決められない）。この検出は P3 の列挙で行う。この関数は座標の解釈だけを提供する。
- 名前の形式に合わないファイル（`r.0.0.mca.bak` など）は、リージョンファイルとして扱わない。
- 外部ファイル: `c.<cx>.<cz>.mcc`。`<cx>`、`<cz>` は絶対チャンク座標。リージョンファイルと同じフォルダに置かれる。

## 構造

### ヘッダー（8192 バイト）

| 範囲 | 内容 |
|---|---|
| 0〜4095 | 位置テーブル。1024 エントリ × 4 バイト。上位 3 バイト（ビッグエンディアン）が開始セクタ、下位 1 バイトがセクタ数。1 セクタ = 4096 バイト |
| 4096〜8191 | タイムスタンプ。1024 エントリ × u32（ビッグエンディアン） |

- エントリが 4 バイトとも 0 なら、そのチャンクは存在しない。
- インデックス `i` と絶対チャンク座標の関係: `cx = rx * 32 + (i & 31)`、`cz = rz * 32 + (i >> 5)`。逆は `i = (cx & 31) + (cz & 31) * 32`。

### チャンクのペイロード

開始セクタ × 4096 の位置から:

| フィールド | 型 | 内容 |
|---|---|---|
| 長さ `L` | u32（ビッグエンディアン） | 次の圧縮方式の 1 バイトを含む長さ |
| 圧縮方式 | u8 | 下の表 |
| データ | `L - 1` バイト | 圧縮されたデータ |

この文書では、「長さ + 圧縮方式 + データ」の `4 + L` バイトを**ペイロード**と呼ぶ。

## 圧縮方式

| 値 | 意味 | 展開 |
|---|---|---|
| 1 | gzip | 実装する |
| 2 | zlib | 実装する |
| 3 | 非圧縮 | 実装する（そのまま） |
| 4 | LZ4（1.20.5 以降） | 実装する（下の「LZ4」） |
| 127 | カスタム。データの先頭に、名前空間つきの識別子がある | 実装しない。「展開できない」として扱う |
| 上記 + 128 | データが外部ファイル `c.<cx>.<cz>.mcc` にある。外部ファイルの中身は、下位 7 ビットの方式で圧縮されたデータそのもの（長さや方式のヘッダーはない） | 外部ファイルを読んでから、下位 7 ビットの方式で展開する |
| その他 | 不明 | 「展開できない」として扱う |

- 外部ファイルを使うチャンクは、リージョンファイルの側に、通常 `L = 1`（圧縮方式の 1 バイトだけ）のペイロードを持つ。
- 展開の API は「ペイロード（と、必要なら外部ファイルの中身）から、展開したバイト列を返す」形にする。展開に失敗した場合は、チャンク単位の内容エラー（下の「エラーの区分」）を返す。

### LZ4

> 要調査: 下の形式は記憶に基づく。実装の前に lz4-java（`net.jpountz.lz4.LZ4BlockOutputStream`）のソースで確認すること。

Minecraft の LZ4 は、LZ4 の標準フレーム形式ではなく、lz4-java の `LZ4BlockOutputStream` の形式である。標準フレームのデコーダーでは読めない。

- ブロックの並び。各ブロックのヘッダーは 21 バイト:
  - マジック `LZ4Block`（8 バイト）
  - トークン（1 バイト）: 上位 4 ビットが方式（`0x10` = 非圧縮、`0x20` = LZ4）、下位 4 ビットが圧縮レベル
  - 圧縮後の長さ（i32、リトルエンディアン）
  - 元の長さ（i32、リトルエンディアン）
  - チェックサム（i32、リトルエンディアン）。既定では XXHash32（シード `0x9747b28c`）の値を `0x0FFFFFFF` でマスクしたもの
- ヘッダーの後に、圧縮後の長さの分のデータが続く。方式が LZ4 ならブロック形式の LZ4 で展開し、非圧縮ならそのまま使う。
- 元の長さが 0 のブロックで終わる。
- チェックサムが合わなければ、内容エラーとする。

## エラーの区分

検査の結果は、**構造エラー**（ファイル単位）と**内容エラー**（チャンク単位）に分ける。この区分は P4 の判定で使う。

### 構造エラー（ファイル単位）

1つでもあれば、そのファイルの構造は信用できない。P4 は、そのファイルを含むリージョン三つ組全体を「そのままコピー」にする。

| ID | 検査 | 条件 |
|---|---|---|
| S-1 | ヘッダーが足りない | ファイルサイズが 1 以上 8192 未満 |
| S-2 | エントリの不正 | 開始セクタとセクタ数の片方だけが 0 |
| S-3 | 範囲外 | 開始セクタが 2 未満 |
| S-4 | 範囲外 | `開始セクタ × 4096 + 4 + L` がファイルサイズを超える。または、長さフィールド自体を読めない（`開始セクタ × 4096 + 5` がファイルサイズを超える） |
| S-5 | 長さの不正 | `L` が 0 |
| S-6 | 長さの不正 | `4 + L` が `セクタ数 × 4096` を超える |
| S-7 | セクタの重複 | 2つのチャンクのセクタの範囲 `[開始, 開始 + セクタ数)` が重なる |
| S-8 | 外部ファイルの欠落 | 圧縮方式が 128 以上なのに、`.mcc` がない |

補足:

- **ファイルの末尾のセクタは、4096 バイトに満たないことがある。** 範囲外かどうかは、セクタ数ではなく、実際の長さ（S-4）で判定する。
- サイズが 0 のファイルは構造エラーではない。「チャンクを持たないファイル」として扱う（P4 の clean の規則で出力から除く）。
- S-6 のうち、セクタ数が 255 で `4 + L > 255 × 4096` のものは、Paper の旧バージョン（1.13〜1.15 頃）の巨大チャンクの可能性がある（要調査: Paper は `r.<rx>.<rz>_oversized.nbt` も置いていた記憶がある）。MVP では構造エラーとして扱い、報告で「Paper 形式の巨大チャンクの可能性」と区別して出す。
- 構造エラーは、見つかったものをすべて集めて返す（最初の1つで止めない）。

### 内容エラー（チャンク単位）

チャンクは「残す」として扱い、ペイロードはそのままコピーできる。ファイルの他のチャンクの処理は続けられる。

| ID | 検査 |
|---|---|
| C-1 | 展開できない（圧縮方式 127、不明な方式、データの破損、LZ4 のチェックサムの不一致） |
| C-2 | NBT として読めない（P2 で検出） |

## 読み取りの API

おおよそ次の形にする（名前は実装で決めてよい）。

- `RegionFile::parse(bytes, rx, rz) -> RegionFile`: ヘッダーを解析し、構造エラーの一覧を持つ。外部ファイルの有無の確認（S-8）には、同じフォルダの `.mcc` の一覧を渡す。
- `entries()`: 存在するチャンクの `(インデックス, 絶対座標, 開始セクタ, セクタ数, タイムスタンプ, L, 圧縮方式)` を返す。
- `payload(index) -> &[u8]`: ペイロード（`4 + L` バイト）を返す。
- `decompress(payload, external: Option<&[u8]>) -> Result<Vec<u8>, ContentError>`。

ファイル全体をメモリに読み込んでよい（リージョンファイルは大きくても数百 MiB）。

## 書き込み（詰め直し）

P7 が使う。残すチャンクのインデックスの集合を受け取り、新しいリージョンファイルのバイト列を作る。

1. ヘッダー（8192 バイト）を 0 で用意する。
2. 残すチャンクを**インデックスの昇順**に並べ、セクタ 2 から順に配置する。
3. 各チャンクのペイロード（`4 + L` バイト）を**元のバイト列のまま**書き、4096 バイトの境界まで 0 で埋める。
4. 位置テーブルに、新しい開始セクタとセクタ数 `ceil((4 + L) / 4096)` を書く。
5. タイムスタンプは、残すチャンクについて元の値を書く。削除したチャンクは 0。
6. 外部ファイルを使うチャンクは、リージョンファイルの側のペイロードをそのまま書く。`.mcc` のコピーは P7 が行う。

- 残すチャンクが1つもなければ、ファイルを作らない（P4 の計画で「出力しない」になる）。
- 削除するチャンクがないファイルは詰め直さず、そのままコピーする（P4 の計画で「そのままコピー」になる）。

## 受け入れ条件

- 合成したリージョンファイルで、S-1〜S-8 のそれぞれが検出され、正常なファイルでは何も検出されない。
- 末尾のセクタが 4096 バイトに満たないファイルを、エラーにしない。
- gzip、zlib、非圧縮、LZ4、外部ファイルのそれぞれのチャンクを展開できる。LZ4 は、lz4-java で作ったデータ（実際のワールドから取ったもの）で確認する。
- 圧縮方式 127 と不明な方式は、内容エラー C-1 になる。
- 詰め直したファイルを解析し直すと、構造エラーがなく、残したチャンクのペイロードとタイムスタンプが元と完全に一致する。
- 詰め直したファイルのサイズは、`8192 + Σ ceil((4 + L) / 4096) × 4096` に一致する。
